# NVD metadata refresh — 5 November 2026

The requested CVE lists come from each original image report's primary IDs, explicit aliases and upstream relationships. The existing image advisory caches were copied before the refresh; the original benchmark data remained unchanged. VigieVuln's `nvd.enrichMatches` warmed the copied caches with the configured NVD mirror-first behavior. The outcome files record 176/176 requested records for Traefik and 103/103 for NGINX.

The compressed JSON files retain the normalized NVD metadata stored by VigieVuln, the individual record IDs, fetch timestamps, cache kind and schema metadata. They are extracted cache records, not raw NVD API documents. NVD metadata adds context and does not establish an OS advisory's affected-version verdict. Multiple CVEs associated with a single distro advisory are retained separately rather than reduced to a fabricated advisory score.

The sample HTML and Word reports were then rendered from the original saved inventories and these warmed caches with `--offline --enrich nvd,kev,epss`. A Node.js network tripwire blocked `fetch` and socket connection attempts and recorded none. Exact package/version/advisory/image identity tuples remain the same as the original scans; severities, CVSS scores and CWE/reference metadata can change because this is a metadata refresh. Unrated advisories without a linked CVE and incomplete-coverage warnings remain visible.

European context was prepared from real local SQL catalogues, retaining their original metadata while copying to the isolated image caches. An incremental direct refresh then obtained the EUVD mapping and exploited pages (19 requests to ENISA), and the two CERT-FR listings (two requests, no revised advisories). Both refreshed catalogues were copied identically between the image caches; request counts, origins, timestamps and compressed-payload SHA-256 hashes are preserved in `eu-cache-copy.json`, `eu-refresh.json` and `eu-refreshed-catalogue.json`. A bounded request limit was not reached. These sources enrich explicit CVE relationships; a derived GCVE-0 identifier is not evidence of a separately fetched GNA advisory.

EUVD detail collection was subsequently attempted independently of NVD for the 273 distinct CVEs across both samples: 184 responses were validated against their EUVD and CVE identities, while 89 were unavailable; sampled failures returned HTTP 403 from ENISA's gateway. The partial outcome is retained in `euvd-details-refresh.json`, and `euvd-targeted-records.json.gz` contains only the validated responses and their source timestamps. No missing detail was synthesized. Both caches also received the 303 real GCVE records and one GNA snapshot already present in the local SQL store; its 4 November source coverage was explicitly partial and stale at replay. Locally derived GCVE-0 identifiers remain distinct from independently fetched GNA records.

The later European-context replay used the same saved inventories with `--offline --enrich nvd,kev,epss,gcve,euvd,certfr`, with the same network tripwire and no connection attempts. NGINX retained 80 raw findings and 155 displayed package/CVE rows. Traefik now has 212 raw findings and 212 displayed rows versus 214 raw observations previously: two GO/GHSA pairs of the same advisory and package were consolidated by alias-aware merging. Their advisory identities remain available as aliases. Thus this second replay changes the raw count by deduplication rather than preserving every original primary-ID tuple.

A later targeted online retry used the existing CVE-to-EUVD relationships and the same isolated caches. NGINX obtained validated details for all 103 linked CVEs. Eight of 176 Traefik details initially exceeded the scanner's 4 MiB metadata limit; after raising the configurable default to 32 MiB, all 176 were validated. ENISA returned HTTP 200 for those eight, whose responses ranged from 4.42 to 13.24 MB. Retry records, including resource identifiers and the original failures, are in `euvd-details-retry-nginx.json`, `euvd-details-retry-traefik.json` and `euvd-details-retry-traefik-32mib.json`. The final offline replay made no network attempts and retained the same 212 and 80 package/advisory identity tuples as the previous replay.
