# Native CNA causes for the 22 confirmed Dubbo/Snyk gaps

This follows [the 38-case adjudication](dubbo-snyk-version-adjudication.md). All 22 gaps have sufficient primary evidence for a human package/advisory adjudication, but **none has a complete exact-package plus evaluable-version proof in the native structured CNA fields consumed by the current v2 pipeline**. Manual review of maintainer statements and exact-version code is not equivalent to an automatically trustworthy package match.

The production functions were invoked read-only on the freshly fetched native records: `isMavenRelevant`, `extractMavenRelevantCve`, `cveEnvelope`, `affectedVerdict` and `matchDepsAgainstCves`. Twenty records are rejected by the Maven relevance filter and produce no package keys. Two Tomcat records become product-derived candidates and remain uncertain. Zero findings are emitted. The [JSON probe](dubbo-snyk-native-cna-causes.json) records each native affected structure, projection, per-range verdict, code-file hash and reason. This is not a full CLI rerun, and does not prove which native revisions the earlier process had cached.

## Generic correction proposal

1. Retain native documents and retrieve related documents by explicit CVE IDs even when the package projection is unavailable. Candidate discovery must remain separate from proof of applicability. Preserve source revisions and rejected records.
2. Expose distinct coverage reasons for missing package identity, unsupported version types, malformed intervals and ambiguous source associations. The current generic partial-source warning cannot explain the individual gap.
3. Require corrected structured source data, or a separately reviewed enrichment dataset with exact package/version evidence and provenance, before converting those candidates to findings. No per-product or per-CVE matching exceptions are justified here.
4. A shared CVE ID is a discovery join, not permission to copy a framework-wide range onto every module listed by another source. In particular, the product map's Tomcat module fan-out must not become exact evidence.

This proposal improves completeness reporting and auditability without adding false positives. It **does not claim to resolve the 22 positive coverage gaps automatically**. Parsing general advisory prose, treating `n/a` as affected-all, reconstructing CBOR's split malformed ranges, ignoring unknown Tomcat branches, or trusting a full Snyk range without primary checks would not satisfy the zero-false-positive constraint. The 13 Snyk errors in the adjacent adjudication demonstrate why adding that source wholesale is insufficient.

For CVE-2024-56337, even accepting the manually verified Tomcat artifact would not alone produce a positive native verdict: the valid 8.5 range is combined with malformed semver lower bounds elsewhere. Changing the comparator's declared semantics or dropping the unknown entries is not a safe generic repair. For the 17 Jackson records and two Spring records, no version-comparison adjustment can recover data that exists only as prose and lacks explicit package identity.
